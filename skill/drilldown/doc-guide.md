# 設計書・仕様書・issue の解説の書き方

ねらい：読み手が文書の大枠をまずつかみ、細かいところは画面の質問スレッドで掘り下げられるようにする。人が決めなければならない事項があれば、判断しやすいよう一か所に集める。

## 1. 元の文書を読む

- リポジトリ内の `.md`：全体を読む。ほかの文書やコードを参照していれば、必要な分だけ読む。
- issue：`gh issue view <番号> --comments`。コメントで決まったこと・覆ったことも拾う。
- Confluence：いつも使っている連携で読む。子ページや添付は、本文の理解に要る分だけ読む。
- 元の場所（パス・URL）は `sources.txt` に1行ずつ書く。

## 2. 解説の組み立て

大枠から細部への順は崩さない。

```markdown
# <文書の題名>
## 一言でいうと        … 何を・なぜを2文以内
## 全体像              … 主要な要素3〜5個。関係や流れが大事なら mermaid 1つ
## 要素ごとの説明      … 各要素について、何をする・何とつながる・前提
## 決める事項          … decisions.json と同じものを一覧（なければ節ごと省く）
## 読むときの注意      … 未定義の用語、他文書への依存、元の文書の曖昧な点
```

### `## 決める事項` の書き方

- `decisions.json` と**同じ並び・同じ題名**にする。見出しは `### d1 <題名>` の形。画面は、見出しが `d1` で始まる節のすぐ下に、その事項の判断を書く欄を出す。見出しの形が違うと、欄は本文の下にまとめて出る。
- 各事項に、元の文書の該当する一文を**そのまま**載せる（`decisions.json` の `quote` はここか本文から写す）。
- 続けて、なぜ決める必要があるかを2〜3文で書き、文書に書かれている選択肢があれば箇条書きで載せる。
- 文書にはっきり書かれていない事項は足さない。足すなら「文書には書かれていないが」と書く。

## 3. 書き方のルール

- 読み手は文を1つ選んで質問するので、**1つの文には1つの内容だけ**を書く。用語は最初に出たところで手短に説明する
- 関数名やファイル名はバッククォートで囲む
- 文書から分からないことは「文書からは読み取れない」と書く。想像で補わない
- 抜粋は実物から写す（コマンドの出力やファイルの中身をそのまま）。1つ15行まで、直前に「どこに注目してほしいか」を一文。フェンスの見出しは「~~~~言語名 ファイルパス:開始行」とし、行番号が実物と一致しているか確かめる
- 元の文書にある数字と結論は書き換えない
- 流れ・構成や関係・数の内訳など、絵で見たほうがつかみやすい箇所には mermaid の図を入れる（`SKILL.md` の §3）
- 抜粋を除いた長さは画面で2〜3枚ぶんにとどめる。すべてを書き尽くそうとしない
- `title.txt` には文書の題名を短くまとめたものを書く
