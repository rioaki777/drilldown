# PR の解説の書き方

ねらい：読み手が PR の大枠をまずつかみ、細かいところは画面の質問スレッドで掘り下げられるようにする。**評価や改善点は書かない（理解のためのスキルで、レビューには使わない）**。

## 1. 何を読むか決める

```bash
# gh が使える場合
gh pr view <番号 or 空> --json number,title,body,author,baseRefName,headRefName,additions,deletions,changedFiles,files,commits
gh pr diff <番号 or 空>

# gh が使えない / PR がない場合
git rev-parse --abbrev-ref HEAD
BASE=$(git merge-base HEAD origin/main 2>/dev/null || git merge-base HEAD main)
git log --oneline "$BASE"..HEAD
git diff --stat "$BASE"...HEAD
git diff "$BASE"...HEAD
```

差分が大きければ、先に `--stat` で全体の形を見て、要になるファイルに絞って読む。足りなければ、変更後のファイル全体や、変更箇所を呼んでいる側も読む。

## 2. 解説の組み立て

大枠から細部への順は崩さない。

```markdown
# <PRのタイトル>（#番号）
## 一言でいうと        … 何を変えるのか・なぜ変えるのかを、合わせて2文まで
## 背景                … PR から分からないことは「PRからは読み取れない」と書く。想像で補わない
## 変更の全体像        … 変更を意味のまとまりに分けて3〜5個、番号を振り、それぞれ2〜4文。処理の流れが変わるなら mermaid を1つ
## 主な変更の中身      … 抜粋は1つ15行まで。直前に「どこに注目してほしいか」を一文。中身はコマンドの出力から写す
                         変更後のコード：sed -n '<開始>,<終了>p' <ファイル> で取り出し、フェンスの見出しは「~~~~言語名 ファイルパス:開始行」
                         差分：フェンスの見出しは「~~~~diff ファイルパス」
## 読むときのポイント  … 影響する範囲・前提になっている仕様・テストが確かめていること・決まっていないこと から3〜5個
## 変更ファイル        … | ファイル | 変更の内容 | 増減 |（増減は --stat の数字。10件を超えたら主なものだけ載せ、残りは「ほかN件」）
```

## 3. 書くときの決まり

- 読み手は文を1つ選んで質問するので、**1つの文には1つの内容だけ**を書く。用語は最初に出たところで手短に説明する
- 関数名やファイル名はバッククォートで囲む
- 処理の流れ・構成・変更の前後など、絵で見たほうがつかみやすい箇所には mermaid の図を入れる（`SKILL.md` の §3）。図にしても数字と結論は PR のままにする
- 見出しに書いた「ファイルパス:開始行」が実物と一致しているか確かめる（画面はこの行番号を表示に使う）
- 抜粋を除いた長さは画面で2〜3枚ぶんにとどめる。すべてを書き尽くそうとしない
- `title.txt` には PR のタイトルを短くまとめたものを書く
- `sources.txt` には PR の URL を書く（PR がなければ、ブランチ名と比較の起点）
